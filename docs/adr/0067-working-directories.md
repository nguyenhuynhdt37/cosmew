# ADR 0067 — Trusted additional directories are working directories

Date: 2026-11-20. Status: accepted. Reverses the file-tool consequence of [ADR 0061](0061-claude-code-permissions-and-sandbox.md) (the sentence that kept `read`, `edit`, `write` and `apply_patch` inside the original workspace root). The trust gate, permission modes, hard denies and the default-on sandbox of ADR 0061 stay. No contract bump (stays 1.37), no new dependency, no settings-merge change.

## Problem

`permissions.additionalDirectories` already widened the command sandbox, and a trusted `sandbox.enabled: false` already launched commands unsandboxed. File, search and LSP tools still called `WorkspaceRoot.resolve` with the session project only, so a path that existed only in a granted directory was `outside-workspace` before policy ran. Turning the sandbox off did not remove that denial, and it made every shell command ask, because auto-allow applies only to sandboxed commands.

## Decision

1. **One working-directory set.** For each call, the set is the session project plus the trusted `permissions.additionalDirectories` already on `SandboxConfig`. `WorkspaceRoot.resolve(input, additional)` and `locateWriteTarget` take that list as an argument. The shared root object does not store it, so a read-only subagent that sets `additionalDirectories: []` (ADR 0061) does not inherit the parent's extra directories. A missing directory, or one equal to the project root, is dropped. When a path is inside the project and a grant, the project wins. Otherwise the longest containing grant wins.
2. **Path shape.** A project-relative path with no `.` or `..` segment stays on the project, including a new file whose parent does not exist yet. Absolute paths and paths that walk through a root are sealed by realpath, so a macOS `/var` vs `/private/var` prefix still matches. A symlink is followed only after the spelled path has entered a working directory. The ledger key and the permission target for a project file stay the project-relative path. For a file in a grant they are the canonical absolute path (`/` separators). Writes keep a `writePath`-safe relative path plus the owning base. `.git`, Futryn/Hannes state and an explicit deny rule are still refused inside a grant: policy runs on that relative path and the real absolute path, unchanged.
3. **Same set for the tools.** Read, Edit, Write, apply_patch, Grep, Glob, LSP read, LSP rename and the command workdir resolve through that set. Grep and Glob walk a granted directory and re-check each hit against it. A rename whose edits stay inside the set is applied; a rename that would change any other path is refused and writes nothing. Shell sandbox writable roots stay this set while the sandbox is on, and are omitted when the command is unsandboxed or read-only. The launch request still carries the same directories as `cwdRoots`, so a workdir inside a granted directory is accepted and the native runtime checks it again. A trusted `sandbox.enabled: false` runs unsandboxed; `default` and `acceptEdits` still ask unless an allow rule or `bypassPermissions` answers. `plan` still refuses edits and commands.
4. **What stays single-root.** Nested instructions, project context and did-you-mean stay on the session project. Language servers still launch and watch that project (`spawnService` and `projectRoot`); a granted file is opened by its absolute URI, and the rename patch is applied by Futryn. An untrusted repository settings file still grants neither extra directories nor `sandbox.enabled: false` until its content hash is trusted. The product default remains sandbox on.

## Evidence and limits

`tests/workspace/working-roots.test.ts` checks the path predicate (project path, grant, third path, symlinks). `tests/security/permission-modes.test.ts` drives the real dispatcher: Read, Edit, Write, apply_patch, Glob, Grep, an LSP hover, an in-roots rename, an outside rename and `exec_command`, including untrusted repository loosening, the unsandboxed prompt, `acceptEdits` without a prompt, `plan`, deny rules, `.git`, Futryn state and sandbox-on auto-allow. The same file drives `NativeCommandRuntime` for an unsandboxed, excluded, and `dangerouslyDisableSandbox` command whose workdir is a granted directory, and for a sandboxed command with that workdir. `tests/security/claude-sandbox.test.ts` ("writes land only in the working directory and additionalDirectories") is the macOS Seatbelt case. Linux bubblewrap and a live language server whose workspace root is the granted directory are **Needs verification**. This ADR does not claim Product MVP completion.
