# ADR 0018: Codex subscription read-only tool bridge

Accepted 2026-11-15 after explicit user approval to extend ChatGPT/Codex reads. Supersedes the all-tools-denied restriction in ADR 0008/0017 and AGENTS.md only for Hannes-owned `read`, `glob`, `grep` callbacks. Other subscription runtimes remain chat-only. Builtin runtime shell/filesystem, write, MCP, plugins and delegated tools stay denied.

The isolated Codex app-server receives experimental dynamic tool descriptors. Its `item/tool/call` requests are converted into the existing Hannes tool call/result events. Core owns execution through the existing ToolPort dispatcher, workspace containment, security policy, redaction and durable audit. Runtime cwd remains the isolated empty profile workspace. No workspace handle or shell is given to Codex. Folder consent is required; sensitive reads retain the existing once/session/deny prompt, and Esc denies. At most 32 inline calls per user turn; duplicate IDs, wrong thread/turn, unknown tools, unsupported namespaces, malformed arguments, cancelled/expired requests and unexpected builtin execution fail closed.

Contract 1.6 adds optional `ModelPort.inlineTools` and an optional third `stream` argument, a process-local tool-execution callback. No callback is serialized in ModelRequest or stored. Existing adapters ignore the optional argument; core and redaction wrapper forward it only for inline-capable models. ModelEvent and Message shapes are unchanged. Tool messages commit with the final answer through the existing store. No database/settings migration or dependency change. Older clients retain chat-only subscription behavior; all deployed consumers must use the new core/models/security composition together to enable the bridge.

Protocol evidence: official installed codex-cli 0.167.0, `codex app-server generate-ts --experimental --out /tmp/hannes-codex-experimental`, accessed 2026-11-15. Types: InitializeCapabilities.experimentalApi, v2/ThreadStartParams.dynamicTools, DynamicToolSpec function variant, DynamicToolCallParams and DynamicToolCallResponse. Experimental protocol compatibility remains bounded to tested fixtures/local schema; live authenticated model tool use must be recorded separately.

Current documentation cross-check through Context7 `/openai/codex`, accessed 2026-11-15: `codex-rs/app-server-protocol/src/protocol/v2/thread.rs` (experimental dynamicTools), `protocol/common.rs` (item/tool/call) and `app-server/src/dynamic_tools.rs` (response decoding). The exact upstream revision is not pinned; installed 0.167.0 generated types are the concrete local compatibility evidence.

## Live evidence (2026-11-15)

A real request through the active local ChatGPT/Codex account read a generated README in an isolated temporary workspace via Hannes `read`. The model returned the exact random marker contained only in that file: one successful read and marker comparison true. No private project files were read. The temporary conversation and directory were deleted. An initial live attempt returned POLICY before any read; a subsequent small chat probe and the final read probe succeeded. This establishes actual local subscription tool use on installed Codex 0.167.0, not cross-version/OS compatibility, all-model entitlement or a Product MVP claim. Runtime credential refresh used the normal vault/lease path; no credentials or raw prompts were printed.

Final validation: `bun run lint` and `bun test tests` pass (246 pass, 5 skip, 0 fail). Three status golden frames intentionally changed to show workspace-read capability; all other golden frames were unchanged. Actual PTY and live Codex reading are separate evidence as described above.

## Project grounding and investigation follow-up (2026-11-15)

The user reported shallow README-only answers and citations pointing into the isolated runtime cwd. Composition now injects the actual approved project root into the Codex bridge on new, forked and resumed conversations. This is metadata, not a cwd change or permission grant. Thread-scoped developer instructions distinguish runtime cwd from the real project, request source/manifest/test evidence appropriate to the question, require checking documentation against implementation, and ask the model to disclose inspection limits. No fixed file-count target, artificial delay or claim of exhaustive review is introduced.

Dynamic tool replies wrap the existing redacted result in a source envelope (workspace root, tool, relative source, status, truncation and untrusted content). Original ToolResult events and stored messages retain their existing schemas. Tests verify trusted metadata remains separate from text that tries to forge a source label. All filesystem and approval boundaries remain unchanged; there is no public contract or database migration.

Live evaluation used the current model/account with a temporary MiniQueue repository. README falsely claimed memory-only storage and no tests. Source implemented a file journal and included a restart test. Asked a normal Vietnamese project-overview question, the real model inspected README, package.json, src/main.ts, src/queue.ts and tests/queue.test.ts, identified both documentation contradictions, traced HTTP enqueue to queue persistence, described implementation gaps, and explicitly said it had read but not run tests. No runtime-tmp path appeared in the answer. The temporary session and files were removed. This is one scoped quality evaluation; it does not quantify parity with Codex or prove exhaustive coverage on arbitrary repositories.

Follow-up validation: `bun run lint` and `bun test tests` pass: **249 pass, 5 skip, 0 fail**, 254 tests across 24 files. Added tests check project instructions, source-envelope integrity and root propagation through new/resumed conversations. The live MiniQueue evaluation above is separate from deterministic fixture coverage.
